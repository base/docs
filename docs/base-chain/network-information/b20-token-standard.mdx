B20 is Base's native token standard: an ERC-20 superset implemented as Rust precompiles rather than deployed Solidity contracts. Running as a precompile makes transfers cheaper and higher-throughput than a standard contract token while keeping full ERC-20 compatibility.

Roles, policy gating, memos, pausing, supply caps, and ERC-2612 `permit` are built into the chain. A standard ERC-20 leaves that logic for you to build, audit, and maintain.

B20 is designed for stablecoin, real-world asset (RWA), and long-tail token issuers. It shipped with the [Beryl upgrade](/base-chain/specs/upgrades/beryl/overview).

## ERC-20 compatibility

B20 is a superset of ERC-20. Standard calls and events keep selector and behavior parity:

`transfer`, `transferFrom`, `approve`, `allowance`, `balanceOf`, `totalSupply`, `name`, `symbol`, `decimals`, `Transfer`, and `Approval`.

B20-specific methods extend the standard without changing the ERC-20 surface, so an app that accepts ERC-20 tokens accepts B20 with no code changes.

<Note>
B20 tokens range from 6 to 18 decimals, so read `decimals()` rather than assuming 18.
</Note>

## What B20 adds to ERC-20

| Feature | Behavior |
|---|---|
| [Roles](/base-chain/specs/upgrades/beryl/b20/specification#roles-model) | Role-based access control with fixed built-in roles. `MINT_ROLE`, `BURN_ROLE`, `SEIZE_ROLE`, `PAUSE_ROLE`, `UNPAUSE_ROLE`, and `METADATA_ROLE` each gate their own operations; `DEFAULT_ADMIN_ROLE` gates role and configuration changes. |
| [Policies](/base-chain/specs/upgrades/beryl/b20/specification#policy-registry) | A singleton PolicyRegistry precompile stores policies addressed by `uint64 policyId`, with `BLOCKLIST`, `ALLOWLIST`, and composite `UNION` and `INTERSECT` types. Tokens call `isAuthorized(policyId, account)` during gated operations. |
| [Policy scopes](/base-chain/specs/upgrades/beryl/b20/specification#policy-integration) | Each token stores one policy ID per scope, covering transfer sender, receiver, and executor, mint receiver, and seize holder and receiver. All default to `ALWAYS_ALLOW`. `approve` and `permit` are not policy-gated. |
| [Seize](/base-chain/specs/upgrades/beryl/b20/specification#seize) | `seizeWithMemo(from, to, amount, memo)` moves a balance and emits `Transfer`, `Memo`, and `Seized`. It skips allowance and transfer policies, requires `from` to be denied by `SEIZE_HOLDER_POLICY`, and requires `to` to be authorized by `SEIZE_RECEIVER_POLICY`. |
| [Granular pause](/base-chain/specs/upgrades/beryl/b20/specification#pause) | Pause by `PausableFeature`: `TRANSFER`, `MINT`, `BURN`, and `SEIZE` independently, rather than halting the whole token. |
| [Memos](/base-chain/specs/upgrades/beryl/b20/specification#memos) | Memo-enabled operations emit `Memo(address indexed caller, bytes32 indexed memo)` immediately after the primary event. Indexers join memo logs to the parent log with `(transactionHash, logIndex - 1)`. |
| [Supply cap](/base-chain/specs/upgrades/beryl/b20/specification#supply-cap) | Optional enforced ceiling on `totalSupply`. The sentinel `type(uint128).max` means no practical cap and is also the maximum permitted supply. |
| [ERC-2612 `permit`](/base-chain/specs/upgrades/beryl/b20/specification#erc-2612-permit--eip-712) | Signed approvals with an EIP-712 domain of `(name, version, chainId, verifyingContract)` and `version` fixed at `"1"`. ERC-1271 contract signatures are not accepted. |
| [Contract URI](/base-chain/specs/upgrades/beryl/b20/specification#contract-uri-erc-7572) | `contractURI()` returns offchain token metadata per ERC-7572, updatable under `METADATA_ROLE`. |
| [Factory](/base-chain/specs/upgrades/beryl/b20/specification#factory) | All tokens are created through a singleton factory precompile via `createB20(variant, salt, params, initCalls)`, which dispatches bootstrap calls so a token arrives configured in one transaction. |

### Deterministic addresses

Token addresses are derived from the deployer and a caller-chosen salt, and encode the variant in the address itself:

```text
[10-byte B20 prefix][1-byte variant][9-byte keccak256(deployer, salt)]
```

The factory exposes `getB20Address`, `isB20`, and `isB20Initialized`, so you can recognize and pre-compute a B20 address before the token exists.

### Admin renunciation

The final `DEFAULT_ADMIN_ROLE` holder cannot be removed with `renounceRole` or `revokeRole`; both revert with `LastAdminCannotRenounce`. `renounceLastAdmin()` is the only normal path to admin-less operation. A token can also launch admin-less by setting `initialAdmin == address(0)` at creation. Afterwards, admin-gated functions are permanently uncallable and admin resurrection is blocked.

## Variants

Every B20 token is one of two variants, chosen at creation.

| Variant | Byte | Decimals | Additional surface |
|---|---:|---|---|
| `ASSET` | `0x00` | 6-18, configured at creation | Multiplier, announcements, batch mint, extra metadata |
| `STABLECOIN` | `0x01` | Fixed 6 | `currency()` |

**Asset** adds `OPERATOR_ROLE` and scaled UI balances. The WAD-precision multiplier scales UI balance reads while raw balances stay unchanged, so a 2-for-1 split is one call rather than a migration or a new contract. `announce` emits `Announcement`, dispatches internal calls, and emits `EndAnnouncement`, which puts a corporate action and its disclosure onchain together. `batchMint` mints to parallel recipient and amount arrays atomically, and `extraMetadata` stores issuer-defined values such as a CUSIP.

**Stablecoin** adds `currency()`, set once at creation and restricted to uppercase `A`-`Z`. B20 validates the code format, not the issuer claim, reserves, legal status, or external registration.

## Precompiles and activation

| Precompile | Address |
|---|---|
| B20Factory | `0xB20f000000000000000000000000000000000000` |
| ActivationRegistry | `0x8453000000000000000000000000000000000001` |
| PolicyRegistry | `0x8453000000000000000000000000000000000002` |

Each variant is gated by the ActivationRegistry, as are state-changing PolicyRegistry calls; registry read functions are always callable. `createB20` reverts with `FeatureNotActivated` if the requested variant is not active on the network, so check `isActivated` for `base.b20_asset` or `base.b20_stablecoin` before deploying.

<Note>
Standard `forge` cannot simulate calls to B20 precompile addresses, because they hold no contract bytecode, and aborts with `call to non-contract address`. Use Base's Foundry build (`base-forge`, `base-cast`, [`base-anvil`](https://github.com/base/base-anvil)), which registers the precompiles into its EVM.
</Note>

## When to use B20

- You need compliance, reconciliation, or corporate-action machinery. It ships as part of the standard, so you don't build and audit a custom contract.
- Your integrators matter. Exchanges, wallets, and indexers wire up one surface that behaves the same across every B20 token.
- Cost matters. B20 runs as a native precompile: cheaper and faster than a contract token.

Because B20 is a superset of ERC-20, choosing it carries no compatibility trade-off.
