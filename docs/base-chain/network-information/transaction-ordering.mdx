title: Transaction Ordering
description: How Base orders transactions, preconfirms transactions with Flashblocks, and applies active inclusion constraints.
---

Transaction ordering describes how a valid transaction moves from submission to an ordered Base L2 block. On Base, the sequencer validates transactions, incrementally orders them into Flashblocks while building the next L2 block, then seals the full L2 block.

Ordering is separate from finality. A transaction can be preconfirmed before the full L2 block seals, included in a sealed L2 block, batched to Ethereum, and then finalized after the Ethereum batch reaches L1 finality. For the guarantees at each stage, see [Transaction Finality](/base-chain/network-information/transaction-finality).

## Sequencer role

The sequencer receives signed transactions, validates them against current account state and network rules, chooses which valid transactions to include, and produces ordered L2 blocks. Validators can independently derive and verify the resulting L2 chain from data posted to Ethereum.

## Flashblocks ordering

The Base sequencer produces Flashblocks every **200ms**, committing to transaction ordering incrementally while the next L2 block is being built. Flashblocks provide preconfirmation signals before the full L2 block seals.

| Term | Definition |
|------|------------|
| **Flashblock** | A 200ms sub-block containing a portion of the full block's transactions |
| **Preconfirmation** | A strong signal that a transaction will be included, before the full L2 block seals |
| **Full Block** | Ten Flashblocks combined to form the complete 2-second L2 block |

| Metric | Value |
|--------|-------|
| Flashblock cadence | ~200ms |
| Flashblock build time (P50) | ~10ms |
| Full block time | 2 seconds |
| Flashblocks per block | 10 |
| Reorg rate | < 0.1% |

<Info>
For how preconfirmed state is exposed to applications, see the [Base RPC Overview](/base-chain/api-reference/rpc-overview#flashblocks-behavior-matrix). For the protocol-level sequencer role, see the [Protocol Overview](/base-chain/specs/protocol/overview#sequencers).
</Info>

There are three important ordering mechanics:

1. **Timing** — Flashblocks are built every 200ms, each ordering a portion of the block. Once built and broadcast, transaction ordering is locked. Later-arriving transactions with higher priority fees cannot be included in earlier Flashblocks.

2. **Gas Allocation** — Each Flashblock has an incrementally increasing gas budget. Flashblock `j` can use up to `j/10` of the full block gas limit, minus gas already consumed by earlier Flashblocks in the same block.

   <Info>
   **Current parameters, last verified 2026-05-08**

   | Network | Full block gas limit | Flashblock 1 cumulative budget |
   |---------|----------------------|--------------------------------|
   | Base Mainnet | 400M gas | 40M gas |
   | Base Sepolia | 1.2B gas | 120M gas |

   Base Sepolia's block gas limit is scheduled to increase every 2 weeks. See the [Configuration Changelog](/base-chain/network-information/configuration-changelog) for network parameter history.
   </Info>

   For example, on Base Mainnet, Flashblock 1 can use up to 40M gas, Flashblock 2 can use up to 80M gas minus gas already consumed by Flashblock 1, and Flashblock 10 can use up to the full 400M gas limit minus gas already consumed.

3. **Incremental ordering** — Flashblocks commit to transaction ordering as the L2 block is being built. Do not assume the sequencer performs one global fee-ranked ordering pass over every transaction that arrives during the full 2 second L2 block interval.

## Inclusion constraints

Transaction inclusion is affected by several constraints:

- **Transaction validity:** invalid nonce, insufficient balance, gas-limit violations, or reverted execution can prevent inclusion.
- **Fee settings:** transactions must satisfy the active fee market. Priority fees can affect inclusion and relative ordering.
- **Arrival timing:** once a Flashblock has been produced, later-arriving transactions should not be assumed to reorder that earlier Flashblock, even if they pay a higher priority fee.
- **Block and Flashblock capacity:** each block and each Flashblock has a finite gas budget.
- **Per-transaction gas maximum:** transactions above the active per-transaction gas cap are rejected before inclusion.

<Note>
Priority fees can affect transaction inclusion and ordering, but Flashblocks are not a formalized priority-fee auction mechanism. For latency-sensitive workflows, arrival timing and propagation path matter alongside fee settings.
</Note>

## What preconfirmation means

When a transaction appears in Flashblocks data, it has been sequencer-ordered into the current block-in-progress. This is a strong preconfirmation signal, not the same thing as sealed L2 block inclusion or finality.

Applications can use Flashblocks-aware RPC endpoints and subscriptions to display faster state updates, pending logs, transaction status, or preconfirmed receipts. They should still reconcile against sealed L2 block data before treating the transaction as fully included.

## Per-transaction gas maximum

Base enforces a per-transaction gas maximum. Transactions that specify a gas limit above the active maximum are **rejected by the mempool before inclusion**. `eth_sendTransaction` or `eth_sendRawTransaction` will return a JSON-RPC error (for example: `exceeds maximum per-transaction gas limit`). This cap does **not** change the block gas limit or the block validity conditions.

| Network | Active per-transaction gas maximum |
|---------|------------------------------------|
| Base Mainnet | 16,777,216 gas (2^24), active since Azul (May 28, 2026 at 18:00 UTC) |
| Base Sepolia | 16,777,216 gas (2^24), active since Azul (April 20, 2026 at 18:00 UTC) |

For the Azul protocol change that enforces the 16,777,216 gas cap, see the [Azul execution engine specification](/base-chain/specs/upgrades/azul/exec-engine#transaction-gas-limit-cap).

Bundler operators for smart contract wallets must configure their systems to limit the bundle size to fit within this cap.

## Practical guidance

Apps and wallets should:

- Submit transactions with realistic fee settings and handle RPC rejection errors clearly.
- Track transactions by hash until a sealed receipt is available.
- If using preconfirmed state, label optimistic UI states and reconcile after L2 inclusion.

Market makers and latency-sensitive systems should:

- Account for transaction propagation and arrival time, not only priority fee.
- Monitor both preconfirmation signals and sealed block receipts.
- Avoid assuming that a later high-fee transaction can reorder already-built Flashblocks.

Infrastructure providers should:

- Expose Standard and Flashblocks endpoint behavior clearly to users.
- Document whether by-hash lookups can return preconfirmed cache data.
- Keep raw Flashblocks stream dependencies separate from application-facing RPC behavior.

## FAQ

<Accordion title="Are Flashblocks optional?">
All Base blocks are built by the Flashblocks builder — Flashblocks are always live. Apps may choose not to rely on preconfirmations and can continue using standard RPCs without any Flashblocks integration.
</Accordion>

<Accordion title="Can the sequencer stop publishing Flashblocks?">
The sequencer will not stop publishing Flashblocks unless an extreme circumstance makes running them unsafe. If this happens, preconfirmations are disabled network-wide and confirmations fall back to standard 2-second blocks. The sequencer continues operating normally.
</Accordion>

<Accordion title="Why do transactions sometimes appear out of order by fee?">
The builder uses an incremental mempool that continuously accepts new transactions while building each Flashblock. Transactions are ordered by fee *at the time they are selected*, not globally across all transactions that arrive during the full 2-second block interval. A later-arriving high-fee transaction may appear after an already-committed lower-fee transaction. This is a deliberate tradeoff — faster inclusion at the cost of occasionally breaking strict priority-gas-auction ordering within a Flashblock.
</Accordion>

<Accordion title="How frequently do Flashblock reorgs happen?">
Base targets a reorg rate of less than 0.1%. A reorg means a transaction appeared in a Flashblock preconfirmation but was not included in the final sealed block. While rare, applications should implement fallback logic for critical operations. Current metrics are available at [base.org/stats](https://base.org/stats).
</Accordion>

<Accordion title="Why is my transaction not landing in the first Flashblock?">
Flashblock 1 can only use 1/10 of the block gas limit. Transactions with large gas limits must wait for a later Flashblock where enough cumulative capacity exists. To maximize chances of early inclusion, keep individual transaction gas limits under 1/10 of the block gas limit.
</Accordion>

<Accordion title="Is there any difference in transaction inclusion for Flashblocks vs. 2-second blocks?">
No significant differences — both order transactions by fee. The main difference is timing: Flashblocks occur every 200ms instead of every 2 seconds.
</Accordion>

<Accordion title="Why are there 11 Flashblock indices (0–10)?">
Index 0 contains only system transactions and does not use any gas limit. Indexes 1–10 are the actual Flashblocks that pull pending transactions from the mempool.
</Accordion>

<Accordion title="Why are there sometimes fewer than 10 Flashblocks?">
This is expected. When the previous block takes longer to build, the system compensates by allocating less time to the next block, resulting in fewer Flashblocks.
</Accordion>

<Accordion title="Can the Flashblock index exceed 10? Is that a bug?">
No, it is not a bug. Seeing indices of 11 or higher is expected behavior caused by sequencer timing drift or slight delays in block finalization. Do not hardcode 10 as the final index — use `payloadId` changes or standard RPC block confirmation as the signal that the block has advanced.
</Accordion>
