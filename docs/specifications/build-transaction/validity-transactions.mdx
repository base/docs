Validity transactions let you submit a signed, time-bounded EIP-8130 transaction with conditions that control when it is eligible for inclusion. They are intended for time-sensitive, state-dependent actions such as backruns, liquidations, and conditional orders.

<Warning>
Validity transactions are experimental. They are currently available only on vibenet. Mainnet and Base Sepolia support is planned with the Cobalt hardfork.
</Warning>

## How Validity Transactions Work

A validity transaction combines three mechanisms:

| Mechanism | Purpose |
| --- | --- |
| EIP-8130 expiry | Limits how long the signed transaction can be included. Expiry is compared with canonical block time. |
| Validity predicates | Keep the transaction ineligible until conditions on state or block position are satisfied. |
| Network tip | Contributes to the transaction's priority score when it competes for inclusion. |

<Steps>
<Step title="Construct and Sign">
Construct and sign an [EIP-8130 transaction](/specifications/native-account-abstraction). Its first call phase must contain one ETH transfer to the Sequencer Fee Vault; later phases contain the application actions.
</Step>

<Step title="Submit with Conditions">
Submit the serialized transaction through `base_sendRawTransactionValidity` with its validity predicates. The method follows `eth_sendRawTransaction` submission semantics.
</Step>

<Step title="Wait for Eligibility">
The builder checks predicates after each transaction. If any predicate is false, the validity transaction is skipped and normal block building continues.
</Step>

<Step title="Include or Expire">
Once every predicate matches, the transaction can compete for inclusion by priority. It expires without executing if it is not included before its EIP-8130 expiry.
</Step>
</Steps>

## Availability and Limits

Validity transactions are not allowlisted. They are subject to Base's standard transaction-submission rate limits, which are not currently documented and may change.

There is no minimum expiry. The current target maximum and default are 60 seconds, but this is configurable; provide an explicit expiry in every transaction. The planned predicate limit is approximately 16 predicates per transaction and remains subject to change.

## Lifecycle

| State | Meaning |
| --- | --- |
| Submitted | The RPC accepts the signed transaction and predicates. |
| Ineligible | At least one predicate does not match at the current candidate insertion point. |
| Eligible | Every predicate matches and the transaction can compete for inclusion. |
| Included | The transaction executes onchain. |
| Expired | Its EIP-8130 expiry has passed. |
| Replaced | A transaction with the same nonce supersedes it under `eth_sendRawTransaction` semantics. |

<Note>
Eligibility does not guarantee inclusion. A transaction can lose to a higher-priority transaction, be skipped during heavy load, be replaced, or expire before it is selected.
</Note>

## Privacy and Block Building

Like other transactions in Base's private mempool, a validity transaction is visible after inclusion in a block. Its additional validity criteria are not recorded onchain.

An ineligible validity transaction does not block ordinary transactions. The builder skips it and continues normal block construction. Under rare conditions such as heavy transaction load, validity transactions can be skipped for the remainder of a Flashblock.
