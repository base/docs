Validity transactions let you submit one signed, time-bounded EIP-8130 transaction with conditions that control when it becomes eligible for inclusion. They are designed for actions that are useful only within a short window or after a specific state change, such as backruns, liquidations, and conditional orders.

<Warning>
Validity transactions are experimental. Supported networks, RPC endpoints, validity-window bounds, and limits will be published before the feature becomes generally available.
</Warning>

## How Validity Transactions Work

A validity transaction combines three mechanisms:

| Mechanism | Purpose |
| --- | --- |
| EIP-8130 validity window | Sets the earliest and latest time at which the signed transaction can execute. |
| Validity predicates | Keep the transaction ineligible until conditions on state or block position are satisfied. |
| Network tip | Contributes to the transaction's priority score when it competes for inclusion. |

<Steps>
<Step title="Construct and Sign">
Construct an [EIP-8130 transaction](/specifications/native-account-abstraction) with a short validity window. Put the sequencer tip in the first phase and the application actions in later phases.
</Step>

<Step title="Submit with Conditions">
Submit the serialized transaction through `base_sendRawTransactionValidity`, along with its validity predicates.
</Step>

<Step title="Wait for Eligibility">
The builder checks the predicates against the block state and position it is currently building. If any predicate is false, the transaction is skipped without stopping normal block building.
</Step>

<Step title="Re-evaluate After Changes">
When an earlier transaction changes relevant state, a skipped validity transaction can be evaluated again. If every predicate now matches, it becomes eligible immediately.
</Step>

<Step title="Include or Expire">
An eligible transaction competes for inclusion using its priority score. If it is not included before its EIP-8130 validity window closes, it expires without executing.
</Step>
</Steps>

## Why Use Validity Transactions

### Application Developers

Replace speculative probe transactions with one conditional submission. This reduces failed or unnecessary transactions during periods of fast-changing state, including market volatility.

### Searchers and Market Makers

Express state-dependent backruns and price the opportunity through a network tip. A transaction can remain dormant until an exchange rate, balance, storage value, block number, or Flashblock position matches its requirements.

### Infrastructure and Service Providers

Wrap a standard RPC submission flow for applications that need conditional, replaceable, time-bounded transactions without building a separate transaction execution system.

## Lifecycle

| State | Meaning |
| --- | --- |
| Submitted | The RPC accepted the serialized transaction and its predicates. |
| Ineligible | At least one predicate does not match the current build state or position. |
| Eligible | Every predicate matches and the transaction can compete for inclusion. |
| Included | The transaction was selected and executed in a block or Flashblock. |
| Expired | Its time or position bounds can no longer be satisfied. |
| Replaced | Another transaction superseded the submitted transaction under the applicable replay or nonce rules. |
| Evicted | Infrastructure removed the transaction before inclusion. |

<Note>
Eligibility does not guarantee inclusion. An eligible transaction can still lose to higher-priority transactions, exceed a block limit, fail validation, be replaced, or reach the end of its validity window.
</Note>

## Privacy and Normal Block Building

Validity submissions are not propagated through ordinary public transaction gossip before inclusion. They are still visible to the RPC, mempool, builder, and infrastructure services that process them.

An ineligible validity transaction does not block eligible ordinary transactions. The builder skips it and continues normal block construction, so validity transactions add conditional behavior without changing the chain's ability to build a block.
