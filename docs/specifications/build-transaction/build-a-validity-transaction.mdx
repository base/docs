This guide explains the confirmed transaction requirements for a validity transaction. Runnable Ethers and Viem examples will be published when the EIP-8130 transaction encoding and the experimental RPC schema are finalized.

<Warning>
Validity transactions are experimental and currently available only on vibenet. Mainnet and Base Sepolia support is planned with the Cobalt hardfork.
</Warning>

## Prerequisites

Before submitting a transaction, you need:

- A vibenet RPC endpoint that supports `base_sendRawTransactionValidity`.
- An EIP-8130-compatible signer and transaction builder.
- An account funded with enough ETH for normal execution fees, the network tip, and any ETH value sent by application calls.

For EIP-8130 account and transaction concepts, see [Native Account Abstraction](/specifications/native-account-abstraction).

## 1. Construct the Transaction

Create a signed EIP-8130 transaction with an explicit expiry. Expiry is evaluated against canonical block time. There is no minimum expiry; the current target maximum and default are 60 seconds, but this value may change.

Use the first call phase for exactly one ETH transfer to the Sequencer Fee Vault. Put application calls in later phases. The ETH transferred in the first phase is the network tip used to prioritize the validity transaction.

## 2. Define Validity Predicates

Supply one or more predicates that describe the state or position required for inclusion. Every predicate must be true at the same candidate insertion point.

```json Position Predicates lines wrap expandable highlight={5,12}
{
  "validity": [
    {
      "type": "block_number",
      "params": {
        "op": "=",
        "value": "0x12345"
      }
    },
    {
      "type": "flashblock_index",
      "params": {
        "op": "=",
        "value": "0x7"
      }
    }
  ]
}
```

Supported predicate types are `balance`, `storage`, `block_number`, and `flashblock_index`. The supported operators are `<`, `<=`, `=`, `!=`, `>`, and `>=`. The planned limit is approximately 16 predicates per transaction and remains subject to change.

For predicate examples and safety guidance, see [Predicates and Safety](/specifications/build-transaction/predicates-and-safety).

## 3. Submit the Signed Transaction

Submit the serialized signed transaction and its predicates through `base_sendRawTransactionValidity`. A successful response returns the transaction hash.

The method follows `eth_sendRawTransaction` semantics for duplicates, nonce handling, cancellation, replay, and replacement. A replacement must increase `maxFeePerGas` by at least 10%; set `priorityFeePerGas` to `0`. The network tip may be raised or lowered in a replacement.

## 4. Wait for Inclusion or Expiry

The builder checks predicates after each transaction. When all predicates match, the transaction can compete for inclusion using `tip / tx.gasLimit`. Ordinary transactions use `priorityFeePerGas` instead and win an equal-priority tie because they have fewer predicates.

A matching predicate does not guarantee inclusion. A transaction can lose priority, be skipped under heavy load for the remainder of a Flashblock, be replaced, or expire.

There is no public pending-status, event, log, or trace API for validity transactions. Use [`eth_getTransactionReceipt`](/base-chain/api-reference/ethereum-json-rpc-api/eth_getTransactionReceipt) to confirm onchain inclusion.
