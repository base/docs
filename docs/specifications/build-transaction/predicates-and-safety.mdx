Validity predicates are inclusion conditions evaluated by the builder. They can keep a signed transaction dormant until account state, contract storage, or a block position matches the transaction's requirements.

Predicates filter eligibility. They do not guarantee that the transaction will be included or that its application calls will succeed.

## Supported Predicates

| Type | Observed value | Parameters |
| --- | --- | --- |
| `balance` | An account's ETH balance | `address`, `op`, `value` |
| `storage` | A masked contract storage value | `address`, `slot`, optional `mask`, `op`, `value` |
| `block_number` | The block number being built | `op`, `value` |
| `flashblock_index` | The Flashblock index being built | `op`, `value` |

Supported comparison operators are `<`, `<=`, `=`, `!=`, `>`, and `>=`.

All predicates in the `validity` array are combined with logical AND. Every predicate must match at the same candidate insertion point.

## Evaluation State

State predicates are evaluated against the builder's current candidate state, not only the state at the start of the block. This candidate state can include the effects of transactions already selected for the same block or Flashblock.

When a predicate does not match, the transaction is skipped. If a later transaction changes the relevant balance or storage location, the skipped transaction can be evaluated again against the updated candidate state.

Predicate order can affect evaluation work because evaluation can stop at the first condition that does not match. Put inexpensive or commonly failing predicates before conditions that require additional state reads.

## Balance Predicate

This predicate becomes true when an address has at least `1 ETH`:

```json Balance Predicate lines wrap expandable highlight={5-7}
{
  "type": "balance",
  "params": {
    "address": "0x1111111111111111111111111111111111111111",
    "op": ">=",
    "value": "0xde0b6b3a7640000"
  }
}
```

An account that does not exist in the observed state has a zero balance.

## Storage Predicate

A storage predicate reads `storage(address, slot)`, applies the mask, and compares the result with `value`:

```text Storage Comparison
(storage value & mask) op expected value
```

```json Storage Predicate lines wrap expandable highlight={5-9}
{
  "type": "storage",
  "params": {
    "address": "0x2222222222222222222222222222222222222222",
    "slot": "0x7",
    "mask": "0xff",
    "op": "=",
    "value": "0x2a"
  }
}
```

Bits set in `value` outside the supplied mask make the predicate unsatisfiable and the request can be rejected.

## Block and Flashblock Predicates

Use two separate predicates when a transaction must target both a block and a Flashblock:

```json Block Position lines wrap expandable highlight={3,10}
[
  {
    "type": "block_number",
    "params": {
      "op": "=",
      "value": "0x12345"
    }
  },
  {
    "type": "flashblock_index",
    "params": {
      "op": "=",
      "value": "0x7"
    }
  }
]
```

Upper-bound position predicates can expire permanently once the builder passes their last satisfiable position. State predicates such as `balance` and `storage` can become true again after later state changes.

## Safety Guidance

### Treat Predicates as Filters, Not Execution Guarantees

A predicate matching does not simulate the complete transaction. Contract calls can still revert, run out of gas, or produce a different result than expected.

### Validate Oracle Assumptions

An oracle storage value may be stale, manipulable, or updated more than once in a block. Include any freshness, round, or source checks needed by the application rather than checking only a price value.

### Account for Same-Block State Changes

Transactions selected before yours can change balances and storage. Use predicates that describe the exact state your application requires, and make the transaction itself validate critical assumptions again during execution.

### Verify Storage Layouts

Proxy upgrades and implementation changes can move or reinterpret storage. Do not depend on a slot unless its layout is stable and controlled. Use a mask when only part of a packed slot is relevant.

### Avoid Uninitialized-State Assumptions

CREATE2 addresses, proxies, and not-yet-initialized contracts can have predictable addresses before they have the expected code or configuration. Checking one zero-valued slot may not prove that a contract is safe to call.

### Use Short Validity Windows

Limit the time during which a signed opportunity remains usable. A short window reduces the chance that changing external assumptions make an old transaction unexpectedly eligible.

### Understand the Privacy Boundary

Validity submissions are not ordinary public-mempool broadcasts, but the RPC and builder infrastructure processing the request can access the transaction and predicates. Do not put secrets in calldata, metadata, or predicate values.
