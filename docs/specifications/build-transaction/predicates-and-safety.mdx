Validity predicates are inclusion conditions evaluated by the builder. They can keep a signed transaction pending until account state, contract storage, or a block position matches the transaction's requirements.

Predicates filter eligibility. They do not guarantee inclusion or successful execution.

## Supported Predicates

| Type | Observed value | Parameters |
| --- | --- | --- |
| `balance` | ETH balance of an address | `address`, `op`, `value` |
| `storage` | A storage slot in a contract | `address`, `slot`, `op`, `value` |
| `block_number` | The block number being built | `op`, `value` |
| `flashblock_index` | The Flashblock index being built | `op`, `value` |

Supported comparison operators are `<`, `<=`, `=`, `!=`, `>`, and `>=`.

All predicates in the `validity` array are combined with logical AND. Every predicate must match at the same candidate insertion point. The planned limit is approximately 16 predicates per transaction; this remains subject to change.

## When Predicates Are Evaluated

The builder checks predicates after each transaction. If a predicate does not match, the transaction is skipped and the builder continues with the next transaction in priority order.

A later transaction can change a balance or storage slot. When that happens, a previously skipped validity transaction can be evaluated again and become eligible immediately in the same Flashblock.

Under rare conditions, including heavy transaction load, validity transactions can be skipped for the remainder of a Flashblock even when their predicates match.

## Examples

### Balance

This predicate is true when the address holds at least one wei:

```json Balance Predicate lines wrap expandable highlight={4,7}
{
  "type": "balance",
  "params": {
    "address": "0x1111111111111111111111111111111111111111",
    "op": ">=",
    "value": "0x1"
  }
}
```

### Storage

This predicate is true when the specified contract storage slot equals the expected value:

```json Storage Predicate lines wrap expandable highlight={4,8}
{
  "type": "storage",
  "params": {
    "address": "0x2222222222222222222222222222222222222222",
    "slot": "0x7",
    "op": "=",
    "value": "0x2a"
  }
}
```

### Block Position

Use separate predicates to require both a block number and a Flashblock index:

```json Block Position lines wrap expandable highlight={4,11}
[
  {
    "type": "block_number",
    "params": {
      "op": "=",
      "value": "0x12345"
    }
  },
  {
    "type": "flashblock_index",
    "params": {
      "op": "=",
      "value": "0x7"
    }
  }
]
```

## Safety Guidance

### Treat Predicates as Filters

A matching predicate does not simulate the complete transaction. The transaction can still fail normal validation, lose priority, or revert during execution. Make the application call validate its critical assumptions as well.

### Validate Oracle Assumptions

If an application uses an oracle value in storage, include the freshness, round, and source checks it needs. A storage value can be stale, manipulated, or updated more than once in a Flashblock.

### Account for State Changes

Transactions that execute before yours can change balances and storage. Describe the state your application needs precisely, and expect that it can change again before execution.

### Verify Storage Layouts

Proxy upgrades and implementation changes can move or reinterpret storage. Do not depend on a storage slot unless its layout is stable and controlled.

### Avoid Initialization Assumptions

CREATE2 addresses, proxies, and uninitialized contracts can have predictable addresses before they have the expected code or configuration. A zero-valued storage slot does not prove that a contract is safe to call.

### Set an Explicit, Short Expiry

Use an explicit expiry that covers the expected opportunity without leaving an old transaction usable longer than necessary. Expiry is evaluated against canonical block time; the current target maximum and default are 60 seconds, and may change.

### Understand the Privacy Boundary

Like other transactions in Base's private mempool, a validity transaction is visible after inclusion in a block. Its validity criteria are not recorded onchain. Do not put secrets in transaction calldata or predicate values.
