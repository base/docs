Validity transactions participate in normal block building, but predicates control when they are eligible and a network tip determines their priority.

<Warning>
Validity transactions are experimental. The current parameters and operational limits may change before general availability.
</Warning>

## Priority Score

The builder orders transactions by priority:

| Transaction | Priority score |
| --- | --- |
| Validity transaction | `tip / tx.gasLimit` |
| Ordinary transaction | `priorityFeePerGas` |

When transactions have the same priority score, the transaction with fewer predicates is ranked first. Ordinary transactions have no predicates, so they win an equal-priority tie against validity transactions.

## Eligibility and Re-evaluation

The builder enforces descending priority order within a Flashblock, except when a validity transaction is delayed because its predicates are not satisfied.

1. The builder evaluates a validity transaction at its candidate insertion point.
2. If every predicate matches, the transaction can be included.
3. If any predicate does not match, the builder skips it and continues with the next transaction.
4. After each transaction, the builder checks predicates again. A skipped transaction can become eligible immediately after an earlier transaction changes relevant state.

A transaction becoming eligible does not reserve blockspace. It can still lose to a higher-priority transaction, be skipped under heavy load for the remainder of a Flashblock, be replaced, or expire.

## Network Tip and Fees

The first call phase of an EIP-8130 validity transaction must contain a single ETH transfer to the Sequencer Fee Vault. This transfer is the network tip used for priority comparison. The precise transaction encoding remains subject to EIP-8130 finalization.

| Outcome | Onchain fee behavior |
| --- | --- |
| Not included | No fees are paid. This includes transactions that are rejected, waiting for predicates, expired, replaced, or skipped. |
| Included | Normal onchain execution fees apply, and the network tip is transferred as part of the transaction. |

## Expiry and Replacement

Expiry is the EIP-8130 transaction expiry, evaluated against canonical block time. There is no minimum expiry. The current target maximum and default are 60 seconds, but the value can be reconfigured; set an explicit expiry rather than relying on the default.

Validity transactions use the same duplicate-submission, nonce, cancellation, replay, and replacement semantics as `eth_sendRawTransaction`. A replacement must increase `maxFeePerGas` by at least 10%. Set `priorityFeePerGas` to `0`; a replacement can raise or lower its network tip.

## Example: A State-Dependent Backrun

A validity transaction can use a `storage` predicate to wait for an earlier transaction to update a contract slot. If the predicate is false, the builder skips the transaction and continues in priority order. After each later transaction, it evaluates the predicate again; if the slot now matches, the validity transaction can compete for immediate inclusion in the same Flashblock.

The predicate does not guarantee inclusion or successful execution. The transaction must still have a competitive priority score, remain within its expiry, and pass normal transaction validation.
