Create and persist one complete `PaymentInfo` before asking the payer to approve collection. Every lifecycle call recomputes the payment ID from this struct, so changing one field identifies a different payment.

## Define the Payment Terms

```solidity PaymentInfo.sol lines wrap expandable highlight={2-5,7-12}
struct PaymentInfo {
    address operator;
    address payer;
    address receiver;
    address token;
    uint120 maxAmount;
    uint48 preApprovalExpiry;
    uint48 authorizationExpiry;
    uint48 refundExpiry;
    uint16 minFeeBps;
    uint16 maxFeeBps;
    address feeReceiver;
    uint256 salt;
}
```

| Field | Requirement |
|---|---|
| `operator` | Account or contract that will submit every operator-only lifecycle call |
| `payer` | Wallet whose tokens the payment collector will collect |
| `receiver` | Merchant address that receives captures after fees |
| `token` | ERC-20 token collected, captured, and refunded |
| `maxAmount` | Maximum collectible amount, limited to `uint120` |
| `preApprovalExpiry` | `authorize` or `charge` must execute strictly before this timestamp |
| `authorizationExpiry` | `capture` must execute strictly before this timestamp; `reclaim` becomes available at or after it |
| `refundExpiry` | `refund` must execute strictly before this timestamp |
| `minFeeBps` | Minimum fee rate for each individual charge or capture |
| `maxFeeBps` | Maximum fee rate for each individual charge or capture, at most 10,000 |
| `feeReceiver` | Fixed recipient, or the zero address to let the operator select one at settlement |
| `salt` | Unique entropy for this checkout attempt |

The expiries must satisfy `preApprovalExpiry <= authorizationExpiry <= refundExpiry`.

## Construct `PaymentInfo`

```typescript payment.ts lines wrap expandable highlight={3-7,9-15}
import { bytesToBigInt, parseUnits } from "viem";

const now = BigInt(Math.floor(Date.now() / 1000));
const paymentInfo = {
  operator: operatorAccount.address,
  payer: payerAddress,
  receiver: merchantAddress,
  token: usdcAddress,
  maxAmount: parseUnits("125.00", 6),
  preApprovalExpiry: now + 15n * 60n,
  authorizationExpiry: now + 7n * 24n * 60n * 60n,
  refundExpiry: now + 45n * 24n * 60n * 60n,
  minFeeBps: 0,
  maxFeeBps: 250,
  feeReceiver: platformAddress,
  salt: bytesToBigInt(crypto.getRandomValues(new Uint8Array(32))),
} as const;
```

Use a cryptographically random salt for every retry, not only every order. Because `hasCollectedPayment` never resets, a voided, reclaimed, or fully refunded payment cannot be reused.

## Calculate the Canonical Payment ID

`getHash` hashes the struct, then binds the result to the current chain ID and `AuthCaptureEscrow` address. The same fields therefore produce different IDs across chains or escrow versions.

```typescript payment-hash.ts lines wrap expandable highlight={4-8}
const paymentInfoHash = await publicClient.readContract({
  address: authCaptureEscrow,
  abi: authCaptureEscrowAbi,
  functionName: "getHash",
  args: [paymentInfo],
});
await paymentStore.create({ orderId, paymentInfoHash, paymentInfo });
```

Persist the hash and every struct field before collection. Later workers should load the stored struct rather than reconstructing expiries or fee fields from current business configuration.

<Note>
`getHash` is a protocol-specific, domain-separated identifier, not an EIP-712 typed-data digest. Collectors use this identifier as part of their own token- or wallet-specific signature schemes.
</Note>

## Set Fee Bounds

The payer approves rate bounds in basis points, but the operator supplies an absolute `feeAmount` in raw token units for each `charge` or `capture`.

```text Fee formula
minimum = floor(amount * minFeeBps / 10_000)
maximum = floor(amount * maxFeeBps / 10_000)
minimum <= feeAmount <= maximum
```

For a 100 USDC capture with `minFeeBps = 100` and `maxFeeBps = 300`, the operator may supply a fee from 1 to 3 USDC.

| Configuration | Effect |
|---|---|
| `minFeeBps == maxFeeBps` | Fixed rate for each charge or capture |
| Both fee bounds are zero | Only a zero `feeAmount` is valid |
| Fixed nonzero `feeReceiver` | The call must pass the same receiver, even when `feeAmount` is zero |
| Zero `feeReceiver` in `PaymentInfo` | The operator may choose the receiver, but a nonzero fee cannot use the zero address |

<Warning>
Fee bounds apply independently to each partial capture. Integer division rounds down. With low-decimal tokens, splitting one capture into many small captures can reduce the aggregate minimum fee. Use a token with sufficient decimals, require a minimum capture size, or constrain operator behavior offchain when aggregate fee guarantees matter.
</Warning>

## Read the Current State

```typescript payment-state.ts lines wrap expandable highlight={1-6}
const [hasCollectedPayment, capturableAmount, refundableAmount] =
  await publicClient.readContract({
    address: authCaptureEscrow,
    abi: authCaptureEscrowAbi,
    functionName: "paymentState",
    args: [paymentInfoHash],
  });
```

Use the state with confirmed protocol events. State alone cannot tell whether a zero `capturableAmount` resulted from a full capture, void, reclaim, or immediate charge.

## Keep Versions Separate

v1.1.0 uses `uint256 feeAmount` in `charge`, `capture`, `PaymentCharged`, and `PaymentCaptured`. v1.0.0 used `uint16 feeBps` at settlement and has different contract addresses and event topics.

<Warning>
Never use a v1.0 ABI with the v1.1.0 escrow address. Old ABIs can decode the new fee field without throwing while assigning it the wrong meaning. Route indexed logs by both contract address and event signature during a migration.
</Warning>
