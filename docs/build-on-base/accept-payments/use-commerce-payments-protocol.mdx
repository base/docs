The Commerce Payments Protocol adds the payment lifecycle that commerce needs but a direct token transfer does not provide. It can reserve payer funds before fulfillment, capture all or part of the reservation, cancel unfulfilled orders, let payers recover abandoned authorizations, and bound refunds and fees onchain.

The protocol is permissionless and immutable. Any account or contract can be an **operator**. The operator submits lifecycle transactions and can pay gas for the payer and merchant, but every payment remains constrained by payer-approved terms.

<Note>
This guide documents the v1.1.0 deployment. The contracts use the same CREATE2 addresses on Base mainnet and Base Sepolia.
</Note>

## Choose a Payment Flow

| Checkout requirement | Protocol flow |
|---|---|
| Fulfill immediately | `charge` collects and settles in one transaction |
| Confirm inventory, tax, shipping, or service delivery later | `authorize`, then one or more `capture` calls |
| Cancel before settlement | `void` returns the remaining escrowed amount |
| Recover funds after an inactive operator | `reclaim` lets the payer withdraw after authorization expiry |
| Reverse a settled amount | `refund` returns up to the captured, unrefunded balance |

A payment can be collected exactly once through `authorize` or `charge`. After collection, it can have multiple partial captures or refunds, but it can never be collected again. Create a new `PaymentInfo.salt` for every checkout attempt.

## Understand the Roles

| Role | Responsibility | Onchain authority |
|---|---|---|
| Payer | Approves payment terms and token collection | Can reclaim remaining escrow after `authorizationExpiry` |
| Receiver | Receives the captured amount after fees | No privileged protocol call |
| Operator | Advances the payment lifecycle and usually pays gas | Can authorize, charge, capture, void, and refund only the payments that name it |
| Fee receiver | Receives the fee portion of a charge or capture | No privileged protocol call |

The payer can be an externally owned account or a smart contract wallet. The receiver and fee receiver do not need to interact with the protocol.

## Understand the Contracts

<Frame>
  <img src="/images/commerce-payments/contracts-architecture.png" alt="Commerce Payments Protocol architecture with AuthCaptureEscrow, token collectors, and per-operator token stores" />
</Frame>

| Component | Purpose |
|---|---|
| `AuthCaptureEscrow` | Validates terms, records payment state, enforces timing and fee bounds, and coordinates token movement |
| Payment collector | Converts a payer's ERC-3009 signature, Permit2 signature, token approval, or spend permission into an exact token transfer |
| Refund collector | Sources refund liquidity after captured funds have already left escrow |
| `TokenStore` | Holds escrowed balances for one operator and only sends tokens when called by `AuthCaptureEscrow` |

The escrow predicts one deterministic `TokenStore` for each operator. Funds from that operator's payments share the store, while `paymentState` maintains per-payment accounting. Stores are separated across operators to reduce cross-operator exposure.

The predicted store can receive tokens before contract code is deployed at that address. `AuthCaptureEscrow` deploys the minimal-proxy store on demand when it first needs to send tokens and emits `TokenStoreCreated`.

## Track the Payment State

```solidity PaymentState.sol highlight={2-4}
struct PaymentState {
    bool hasCollectedPayment;
    uint120 capturableAmount;
    uint120 refundableAmount;
}
```

| Field | Meaning |
|---|---|
| `hasCollectedPayment` | Permanently becomes `true` after the first successful `authorize` or `charge` |
| `capturableAmount` | Funds currently in escrow that can still be captured, voided, or reclaimed |
| `refundableAmount` | Cumulative captured amount that the protocol still permits the operator to refund |

`refundableAmount` is an accounting limit, not refund liquidity held in escrow. Capture sends tokens to the receiver and fee receiver. A later refund collector must bring replacement liquidity back into the operator's token store before the protocol forwards it to the payer.

## Know the Trust Boundaries

The protocol prevents an operator from changing the payer, receiver, token, maximum amount, expiry windows, or fee bounds of a signed payment. It also prevents over-capture and over-refund.

The protocol does not guarantee that an operator will act. An operator can refuse to authorize, capture, or refund; can void an authorization before fulfillment; and can select any fee allowed by the payment terms. The payer's fallback is `reclaim` after authorization expiry.

Use a low, commercially justified `maxFeeBps` and fix `feeReceiver` whenever possible. The contract permits a payer to approve fees up to 100%, so an overly broad fee range can let a compromised operator route the entire capture as fees. A zero `feeReceiver` improves liveness because the operator can replace a denylisted recipient, but it also lets the operator choose any fee recipient within the approved bounds.

<Warning>
Token collectors are trusted by the payer, even though the escrow does not trust them. Only use collectors that bind authorization to the complete payment and restrict collection to `AuthCaptureEscrow`. An unsafe collector can misuse a payer's signature or allowance outside the intended payment.
</Warning>

The escrow measures its token store balance before and after collection and requires an exact increase. Fee-on-transfer tokens and other tokens that do not deliver the requested amount are therefore incompatible with the deployed collectors.

There is no protocol administrator, pause switch, collector allowlist, or upgrade path. Pin the escrow, collector, ABI, and version together in application configuration, and migrate to a new deployment explicitly.
