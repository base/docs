Watch the v1.1.0 `AuthCaptureEscrow` address, not token addresses. All six lifecycle events share the indexed `paymentInfoHash`, giving you one payment-centric stream across collectors and tokens.

## Index the Protocol Events

| Event | Lifecycle meaning |
|---|---|
| `PaymentAuthorized` | Payer funds entered escrow and became capturable |
| `PaymentCharged` | Funds were collected and settled immediately |
| `PaymentCaptured` | Some escrowed funds settled to the receiver and fee receiver |
| `PaymentVoided` | The operator returned the remaining authorization |
| `PaymentReclaimed` | The payer recovered the remaining authorization after expiry |
| `PaymentRefunded` | A refund collector sourced funds and the protocol returned them to the payer |

Also index `TokenStoreCreated` for operational monitoring, but do not treat it as a payment state transition.

## Backfill Confirmed Logs

```typescript index-commerce-payments.ts lines wrap expandable highlight={8-17,20-24}
export async function syncCommercePayments(store: EventStore) {
  const head = await publicClient.getBlockNumber();
  if (head <= confirmationDepth) return;

  const toBlock = head - confirmationDepth;
  const cursor = await store.lastCanonicalBlock();
  const fromBlock = cursor > deploymentBlock
    ? cursor - overlapBlocks
    : deploymentBlock;

  const logs = await publicClient.getContractEvents({
    address: authCaptureEscrow,
    abi: authCaptureEscrowAbi,
    fromBlock,
    toBlock,
    strict: true,
  });

  await store.replaceCanonicalRange({
    chainId: base.id,
    contract: authCaptureEscrow,
    fromBlock,
    toBlock,
    logs,
  });
}
```

`replaceCanonicalRange` should run in one database transaction: remove previously indexed rows in the overlap, insert the logs returned from the canonical chain, reduce affected payment state, and advance the cursor only after all writes succeed.

## Use Subscriptions Only as Wakeups

```typescript watch-commerce-payments.ts lines wrap expandable highlight={1-7}
const unwatch = publicClient.watchContractEvent({
  address: authCaptureEscrow,
  abi: authCaptureEscrowAbi,
  onLogs: () => void syncCommercePayments(store),
  onError: (error) => logger.error({ error }, "payment subscription failed"),
});
```

A WebSocket event reduces latency but is not the source of truth. Disconnects, provider limits, and reorgs can drop or replace notifications. Always converge through `eth_getLogs` or `getContractEvents` over a confirmed overlap window.

## Store Stable Event Identity

Use all of these fields:

- Chain ID
- Escrow contract address
- Block hash and block number
- Transaction hash
- Log index
- Event name and indexed `paymentInfoHash`

Transaction hash alone is insufficient because one transaction may emit multiple protocol events or multiple logs relevant to accounting.

## Route v1.0 and v1.1 Separately

The v1.1.0 deployment uses a new escrow address and changes `PaymentCharged` and `PaymentCaptured` from a `uint16 feeBps` field to a `uint256 feeAmount` field. Their event signatures and `topic0` values therefore differ.

| Version | Escrow address on Base and Base Sepolia |
|---|---|
| v1.0.0 | `0xBdEA0D1bcC5966192B070Fdf62aB4EF5b4420cff` |
| v1.1.0 | `0xf96815976523E00e65Be8f34cA5e64b4f41EB19c` |

| Event | v1.0 `topic0` | v1.1 `topic0` |
|---|---|---|
| `PaymentCharged` | `0x943ae4341dd799d7aeedc501f616cd26b134639e0bc2ec059581ba3ebbf1e7d0` | `0x137b0e73e4453f43c2e1ad2552980a0e0c7e988764619974ca26d37a7159940c` |
| `PaymentCaptured` | `0xe749f7bbd01b49bb05abf26ca492cb4dfdea6bedeada8a40fdccd478c73a74e2` | `0xac1e0db1957daedbc6944bcb4c8dc947ff8101d710671ac2ec26309f7f38d58e` |

<Warning>
An old ABI may decode the v1.1 fee field without throwing but interpret raw token units as basis points. Key decoders by `(contract address, event signature)` and never mix ABIs across versions.
</Warning>

## Monitor Failure Conditions

Alert when:

- An authorization approaches `authorizationExpiry` with a nonzero capturable balance.
- A refund approaches `refundExpiry` while customer service still considers it open.
- Collection or lifecycle transfers repeatedly revert because of a token denylist.
- State reconstructed from events differs from `paymentState(paymentInfoHash)`.
- One operator's token store balance is below aggregate capturable accounting for a token.

Continue with [reconcile payments](/build-on-base/accept-payments/reconcile-payments).
