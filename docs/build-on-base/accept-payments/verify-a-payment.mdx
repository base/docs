Use `AuthCaptureEscrow` events as the canonical record of payment lifecycle operations. Raw ERC-20 transfers are not sufficient because collectors and token stores produce different transfer shapes, and a transfer alone does not identify the protocol operation or payment terms.

## Define the Expected Payment

Load the exact `PaymentInfo` and canonical hash stored when the checkout was created.

```typescript expected-payment.ts lines wrap expandable highlight={1-7}
const expectedHash = await publicClient.readContract({
  address: authCaptureEscrow,
  abi: authCaptureEscrowAbi,
  functionName: "getHash",
  args: [storedPaymentInfo],
});
if (expectedHash !== order.paymentInfoHash) {
  throw new Error("Stored payment terms do not match the order");
}
```

Also fix the expected chain ID and v1.1.0 escrow address in server configuration. The hash is bound to both, but verification must reject receipts from another chain before decoding.

## Verify a Lifecycle Transaction

```typescript verify-protocol-payment.ts lines wrap expandable highlight={10-19,22-27}
export async function verifyProtocolOperation(args: {
  hash: Hash;
  expectedEvent: "PaymentAuthorized" | "PaymentCharged" | "PaymentCaptured";
  paymentInfoHash: Hash;
  store: PaymentStore;
}) {
  const receipt = await publicClient.waitForTransactionReceipt({
    hash: args.hash,
    confirmations: 2,
  });
  if (receipt.status !== "success") throw new Error("Payment transaction reverted");

  const events = parseEventLogs({
    abi: authCaptureEscrowAbi,
    logs: receipt.logs.filter(
      (log) => log.address.toLowerCase() === authCaptureEscrow.toLowerCase(),
    ),
    strict: true,
  });
  const operation = events.find(
    (event) => event.eventName === args.expectedEvent &&
      event.args.paymentInfoHash === args.paymentInfoHash,
  );
  if (!operation) throw new Error("Expected protocol operation not found");

  if (!(await args.store.claimOnce(args.paymentInfoHash, args.hash, operation.logIndex))) {
    throw new Error("Payment operation was already processed");
  }
  return { receipt, operation };
}
```

`claimOnce` must rely on a database uniqueness constraint. Use `(chainId, escrowAddress, transactionHash, logIndex)` as the event identity and separately enforce the order transitions permitted for each `paymentInfoHash`.

## Validate Operation-Specific Fields

| Event | Fields to compare with the order |
|---|---|
| `PaymentAuthorized` | Full `PaymentInfo`, authorized amount, collector, and hash |
| `PaymentCharged` | Full `PaymentInfo`, charged amount, collector, absolute fee, fee receiver, and hash |
| `PaymentCaptured` | Hash, gross capture amount, absolute fee, and fee receiver |
| `PaymentVoided` | Hash and returned capturable amount |
| `PaymentReclaimed` | Hash and returned capturable amount |
| `PaymentRefunded` | Hash, gross refund amount, and refund collector |

The initial authorization or charge event contains the full `PaymentInfo`. Later events contain only the hash, so join them to the immutable terms stored for that hash.

## Read State as a Cross-Check

```typescript verify-payment-state.ts lines wrap expandable highlight={1-6}
const [hasCollectedPayment, capturableAmount, refundableAmount] =
  await publicClient.readContract({
    address: authCaptureEscrow,
    abi: authCaptureEscrowAbi,
    functionName: "paymentState",
    args: [order.paymentInfoHash],
  });
```

Use state to confirm amount invariants, not to infer event history. For example, `capturableAmount == 0` can mean immediate charge, full capture, void, or reclaim.

## Gate Fulfillment by the Correct Event

| Business action | Required confirmation |
|---|---|
| Reserve inventory or begin protected fulfillment | Confirmed `PaymentAuthorized` with enough `capturableAmount` |
| Treat an immediate checkout as paid | Confirmed `PaymentCharged` |
| Ship or deliver a captured increment | Confirmed `PaymentCaptured` for that increment |
| Close a canceled authorization | Confirmed `PaymentVoided` or `PaymentReclaimed` |
| Mark a return paid | Confirmed `PaymentRefunded` and transfer to the stored payer |

<Warning>
Do not fulfill from a payer signature, submitted transaction hash, client callback, or unconfirmed subscription event. Only a canonical successful protocol event proves the state transition.
</Warning>

Choose a confirmation policy that matches fulfillment value and reversibility. See [transaction finality](/specifications/transactions/transaction-finality).
