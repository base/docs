---
title: "Authorize a Payment"
keywords: ["Commerce Payments authorize", "escrow USDC payment", "PaymentAuthorized", "authorize capture Base"]
description: "Move payer funds into Commerce Payments Protocol escrow so the operator can capture them after fulfillment."
---

Use `authorize` when settlement must wait for inventory, tax, shipping, service completion, or another fulfillment decision. A successful authorization moves tokens into escrow immediately, so later capture does not depend on the payer keeping funds in their wallet.

<Warning>
A collector signature by itself is not an authorization. Funds become guaranteed for capture only after the `authorize` transaction succeeds and the operator's token store receives them.
</Warning>

## Prepare the Authorization

1. [Configure `PaymentInfo`](/build-on-base/accept-payments/configure-a-payment) with a short pre-approval window and a fulfillment-appropriate authorization window.
2. [Prepare `collectorData`](/build-on-base/accept-payments/choose-a-token-collector) for the payer's token and wallet.
3. Choose an authorization `amount` no greater than `paymentInfo.maxAmount`.
4. Persist the payment terms before submitting from `paymentInfo.operator`.

## Move Funds into Escrow

```typescript authorize-payment.ts lines wrap expandable highlight={4-8}
const amount = parseUnits("125.00", 6);
const { request } = await publicClient.simulateContract({
  account: operatorAccount,
  address: authCaptureEscrow,
  abi: authCaptureEscrowAbi,
  functionName: "authorize",
  args: [paymentInfo, amount, paymentCollector, collectorData],
});
const hash = await operatorWallet.writeContract(request);
const receipt = await publicClient.waitForTransactionReceipt({ hash, confirmations: 2 });
if (receipt.status !== "success") throw new Error("Payment authorization reverted");
```

The escrow records state before calling the collector, but the whole transaction reverts if collection fails. The non-reentrancy guard prevents the collector from entering another lifecycle operation during collection.

## Verify the Reservation

```solidity PaymentAuthorized.sol lines wrap expandable highlight={2-5}
event PaymentAuthorized(
    bytes32 indexed paymentInfoHash,
    PaymentInfo paymentInfo,
    uint256 amount,
    address tokenCollector
);
```

After confirmation, the payment state is:

```text State after authorization
hasCollectedPayment = true
capturableAmount = amount
refundableAmount = 0
```

You can also read the operator store address with `getTokenStore(paymentInfo.operator)` and confirm the token balance, but use `paymentState` for per-payment accounting because one store can hold funds for many payments.

<Check>
Begin protected fulfillment only after the confirmed event matches the stored payment, `capturableAmount` covers the order, and your backend records the authorization idempotently.
</Check>

## Understand Amount Collection

The requested `amount` may be lower than `maxAmount`. Collector behavior differs:

| Collector | What leaves the payer during authorization |
|---|---|
| ERC-3009 | Pulls `maxAmount`, returns the difference, and leaves `amount` in escrow |
| Permit2 | Pulls only `amount`, bounded by the signed `maxAmount` |
| Pre-approval | Pulls only `amount` through the token allowance |
| Spend permission | Spends only `amount` from the configured allowance |

## Handle Common Reverts

| Error | What to check |
|---|---|
| `ExceedsMaxAmount` | Requested authorization is greater than `maxAmount` |
| `AfterPreApprovalExpiry` | Operator submitted after the payer's collection approval expired |
| `InvalidExpiries` | The three expiry timestamps are not ordered |
| `PaymentAlreadyCollected` | The payment hash was previously authorized or charged |
| `InvalidCollectorForOperation` | Collector does not report the payment type |
| `TokenCollectionFailed` | Token store did not receive the exact requested amount |
