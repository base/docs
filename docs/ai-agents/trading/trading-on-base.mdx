Base offers trading agents two structural advantages over most EVM chains: **Flashblocks** (200ms preconfirmed block state, 10× faster than the 2-second block time) and an exposed L1/L2 fee structure that lets agents make explicit cost-vs-speed tradeoffs. This page covers what's specific to Base — for standard EVM execution patterns, the [Ethereum documentation](https://ethereum.org/developers/docs) applies without modification.

---

## Flashblocks: the execution edge

Base blocks are built in 200ms intervals called Flashblocks. Each Flashblock seals a portion of the 2-second block, locking in transaction order for that slice.

**What this means for agents:**

| Behavior | Implication |
| -------- | ----------- |
| Transactions ordered within a 200ms window, not a 2-second block | Priority fee competition is per-Flashblock, not per-block |
| Once a Flashblock seals, its order is final | A later higher-fee transaction cannot displace a transaction already in a sealed Flashblock |
| `"pending"` state on a Flashblocks endpoint reflects the actively building Flashblock | Agents can observe block composition ~200ms before it seals |
| Each Flashblock can use up to 1/10 of the block gas limit (currently **14 million gas**) | Transactions over 14M gas must wait for a Flashblock with enough accumulated headroom |

**Timing model:**
```
[0ms]    Flashblock N seals — order locked, preconfirmation issued
[0-200ms] Flashblock N+1 being built — submit now to target this window
[200ms]  Flashblock N+1 seals
...
[2000ms] Full L2 block seals (contains ~10 Flashblocks)
```

For latency-critical submissions, subscribe to `newFlashblocks` via WebSocket on a Flashblocks-aware endpoint and submit immediately after a seal event — this maximizes the window available for your transaction to land in the next Flashblock:

```typescript
const ws = new WebSocket('wss://mainnet-preconf.base.org');
ws.onopen = () => ws.send(JSON.stringify({
  jsonrpc: '2.0', id: 1,
  method: 'eth_subscribe',
  params: ['newFlashblocks'],
}));
ws.onmessage = (event) => {
  const msg = JSON.parse(event.data);
  if (msg.method === 'eth_subscription') {
    // Flashblock sealed — 200ms window opens for next one
    submitTrade();
  }
};
```

See the [Flashblocks API Reference](/base-chain/flashblocks/api-reference) for full subscription types including `newFlashblockTransactions` and `pendingLogs`.

## Fee mechanics

Base transactions have two cost components. Agents that only set L2 fees will underestimate total cost, particularly during Ethereum congestion when the L1 component can exceed the L2 component.

| Component | Controlled by | Varies with |
| --------- | ------------- | ----------- |
| L2 execution fee | `maxFeePerGas` / `maxPriorityFeePerGas` | L2 congestion |
| L1 data availability fee | Automatically deducted | Ethereum L1 base fee + blob market |

### Setting L2 fees

Use `eth_feeHistory` to compute priority fees from recent blocks rather than guessing:

```json
{"jsonrpc":"2.0","method":"eth_feeHistory","params":[10,"latest",[50,90]],"id":1}
```

- **50th percentile reward** — standard inclusion within 1–3 Flashblocks
- **90th percentile reward** — fast inclusion within the next Flashblock
- **`maxFeePerGas`** — set to `nextBaseFee * 2 + maxPriorityFeePerGas` to survive base fee increases across multiple blocks

The minimum base fee on Base is **0.005 gwei** (5,000,000 wei). The base fee can increase by at most **4% per block**. See [Network Fees](/base-chain/network-information/network-fees) for full EIP-1559 parameters.

### Estimating the L1 fee

Query the **GasPriceOracle** predeployment before signing to understand the L1 cost:

**Address:** `0x420000000000000000000000000000000000000F` (same on all networks)

| Method | Use |
| ------ | --- |
| `getL1FeeUpperBound(uint256 txSize)` | Quick upper-bound estimate from approximate tx byte length |
| `getL1Fee(bytes)` | Exact estimate from fully serialized transaction |
| `l1BaseFee()` | Current Ethereum L1 base fee as seen by Base |
| `blobBaseFee()` | Current EIP-4844 blob base fee |

**Decision rule:** If `l1FeeUpperBound / (gasLimit * maxFeePerGas + l1FeeUpperBound) > 0.8` and trade size is small, the L1 fee dominates — consider deferring until Ethereum congestion subsides.

## Base-specific error handling

These errors are specific to Base or require Base-specific resolution. For a full error taxonomy and retry policy table, see [Troubleshooting Transactions](/base-chain/network-information/troubleshooting-transactions).

| Error | Cause | Resolution |
| ----- | ----- | ---------- |
| `replacement transaction underpriced` | Replacing a pending tx requires ≥10% higher `maxFeePerGas` **and** `maxPriorityFeePerGas` | Increase both by ≥10%, resubmit with same nonce |
| `exceeds maximum per-transaction gas limit` | Gas limit above Base's 25M cap | Reduce gas limit or split transaction |
| `transaction underpriced` | `maxFeePerGas` below current base fee (min 0.005 gwei) | Re-fetch base fee, rebuild transaction |
| DA throttling (no specific error code) | Sequencer limiting L2 throughput to manage L1 data availability | No fee increase resolves this — wait for throttle to lift |

**Nonce management:** Always fetch nonce with `eth_getTransactionCount(address, "pending")`, not `"latest"`. For concurrent submissions, track nonce locally and increment atomically — fetching fresh on each parallel call returns the same value for all.

## Strategy discovery: Base-specific signals

Base exposes data that most chains don't provide with this resolution. The table below maps each signal to the class of opportunity it enables.

| Signal | How to access | Opportunity category |
| ------ | ------------- | -------------------- |
| Preconfirmed pending block state (200ms early) | `eth_getBlockByNumber("pending")` on `mainnet-preconf.base.org` | Detect price impact before block seals; act on state changes visible to no one else |
| Preconfirmed transaction stream | `eth_subscribe("newFlashblockTransactions")` | First-mover on large trades entering the block |
| Preconfirmed logs | `eth_subscribe("pendingLogs", { address, topics })` | Detect liquidation thresholds, pool price events, oracle updates before finality |
| Fee spike detection | `eth_feeHistory` trend over last 5 blocks | Identify congestion onset; adjust routing or pause/resume based on cost conditions |
| L1 base fee trend | `GasPriceOracle.l1BaseFee()` polled over time | Time submissions to minimize L1 data cost; small trades become viable when L1 fee drops |
| Block gas utilization | `gasUsedRatio` from `eth_feeHistory` | Predict upcoming fee increases; calibrate urgency |

**The Flashblocks advantage:** Most chains have a single pool of pending transactions with uncertain ordering. On Base, the Flashblocks endpoint gives agents a deterministic, ordered view of the next 200ms of chain state before it finalizes. This creates an information edge that doesn't exist on chains with only mempool visibility.

**On emerging edges:** Execution speed and fee optimization are table stakes. The more durable edge for LLM-based agents is likely in interpreting *why* chain state is changing — correlating onchain signals (large pending swaps, oracle updates, liquidation proximity) with offchain information (sentiment, protocol governance, cross-chain flows) faster than any human or rule-based system can. The signals above are the raw inputs; the synthesis is where the edge lives.
