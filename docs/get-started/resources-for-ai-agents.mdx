Use this page as the starting point when you want an AI assistant to build on Base. It covers three ways to give an assistant Base context: static docs files, a live MCP connection, and installable skills. You'll also find recommended entry points for common workflows.

## Quick Setup

Get your agent connected to Base docs in one command. Pick the method that fits your tool.

### MCP Server

A live connection lets your assistant search and read Base docs on demand, so it always has current information.

<CodeGroup>
```sh Claude Code
claude mcp add --transport http base-docs https://docs.base.org/mcp
```

```sh Codex CLI
codex mcp add base-docs --url https://docs.base.org/mcp
```

```json Cursor / manual config
{
  "mcpServers": {
    "base-docs": {
      "url": "https://docs.base.org/mcp"
    }
  }
}
```
</CodeGroup>

See the [full MCP setup guide](/get-started/docs-mcp) for Cursor, Windsurf, and other editors.

### Skills

Skills are installable agent workflows for common Base tasks, including connecting to Base, deploying contracts, running a node, and more. They give your assistant step-by-step procedural guidance instead of requiring it to piece together docs on its own.

```sh Terminal
npx skills install base/skills -g
```

Browse available skills in the [Base skills repository](https://github.com/base/skills).

## Give agents bounded spending power

An autonomous agent should not receive an unrestricted wallet allowance. Give it the smallest authority that can complete its job, and keep the final authorization boundary explicit and revocable.

### Production checklist

- **Separate identity from authorization.** A valid session, SIWE signature, or agent key identifies the caller; it should not by itself authorize arbitrary token transfers.
- **Limit the permission.** Bind the permission to the intended token, approved recipient or recipients, maximum amount per call, total amount per period, and an expiry time.
- **Use the wallet-returned permission.** When capabilities can substitute a smart-wallet account, persist and display the account and permission hash returned by the wallet rather than the pre-request values.
- **Treat prepared calls as variable length.** A first use may need a permission-registration call plus the spend call. Later uses may need only the spend call. Pass the returned calls array through unchanged instead of destructuring fixed positions.
- **Check status before every spend.** Reject expired, revoked, or otherwise inactive permissions immediately before submitting the transaction, and surface the exact amount and recipient to the user or operator.
- **Make recovery easy.** Provide a clear revoke path and keep allowances narrow enough that revoking one permission does not require trusting an unrelated application session.

For production agents, test both the first-use and repeat-use paths, plus blocked recipients, amount-limit failures, expiry, revocation, smart-wallet signatures, and insufficient allowance. These checks catch the most dangerous failure mode: an agent that appears bounded in the UI but can submit a broader call than the user intended.
